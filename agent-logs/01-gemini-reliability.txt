  Plan

  1. GeminiVisionClient.java
  - Pure decision functions (package-private and static, so they can be tested):
    - isRetryable(int status) is true only for 503 and 429.
    - isSchemaRejection(int status, String body) is true only when the status is
      400, the error message mentions the response schema (response_schema /
      responseSchema / generation_config), and no details[].reason equals
      API_KEY_INVALID.
    - errorMessage(String body, String apiKey) pulls out error.message, or a
      truncated raw body if it isn't JSON. It replaces the key, and anything
      shaped like a Google key (AIza…), with [redacted], and caps the length at
      about 500 characters.
  - Retry loop: at most 3 attempts in total, with sleeps of 2 s and then 5 s,
    only when isRetryable is true. I'm reading "up to 3 times with backoff 2 s
    and 5 s" as 3 attempts and 2 waits. If you meant 3 retries after the first
    try, tell me.
  - Schema fallback: only when isSchemaRejection is true. The fallback request
    goes through the same retry loop. Every other 400 (bad key, bad image and so
    on) fails right away with 503 and no fallback.
  - Timeouts and network errors:
    - I catch HttpTimeoutException, then other IOExceptions, and also
      InterruptedException (restoring the interrupt flag).
    - Each one is logged and rethrown as VisionUnavailableException, which
      ErrorHandler already turns into 503.
    - Timeouts are not retried, since you asked for retries only on 503/429.
      With the current 150 s timeout, retrying them could take about 7.5
      minutes.
  - Testability: I add a package-private constructor that takes a small Sender
    interface (request → status and body) and a Sleeper. Tests can then run the
    loop with canned responses, with no network and no real sleeping. The Spring
    constructor stays the same.
  - Messages to the app stay generic, e.g. "Gemini returned HTTP 429 after 3
    attempts" or "Gemini timed out after 150 s". Gemini's own error text goes
    only to the log.

  2. VisionLog.java
  - Add attempts, errorKind (http | timeout | network | interrupted) and error
    (the redacted Gemini message) to each line. Success lines keep their current
    fields and gain attempts. Error lines use status: 0 when there was no HTTP
    response.

  3. ErrorHandler.java
  - Probably no change. Timeouts reach it as VisionUnavailableException, which
    already returns 503. I'm deliberately not adding a catch-all IOException → 
    503, because that would also turn unrelated errors (such as a broken
    multipart upload) into "vision unavailable". The API contract in PLAN.md §5
    doesn't change.

  4. Tests: new GeminiRetryTest.java
  - isRetryable: true for 503 and 429; false for 500, 400 and 404.
  - isSchemaRejection: true for a real schema-error body; false for an
    API_KEY_INVALID body, a non-schema INVALID_ARGUMENT (e.g. the image), and
    non-400 statuses.
  - Retry loop:
    - 503, 503, 200 → success after 3 calls, sleeps of [2 s, 5 s]
    - 503 ×3 → 503 to the client
    - 429 then 200 → success
    - 500 → only 1 call
  - Fallback: a schema 400 makes a second call without responseSchema, logged
    with schemaUsed: false. An API_KEY_INVALID 400 → 1 call and no fallback.
  - Timeout and ConnectException → VisionUnavailableException, and a log line
    with the right errorKind.
  - Logs use @TempDir. One test asserts that the log contains Gemini's message
    and never the fake API key, even when the error body echoes the key back.

  What changed
  - GeminiVisionClient.java
    - Retries: HTTP 503 and 429 are retried with waits of 2 s and then 5 s, for
      at most 3 attempts in total. Every other status fails at once.
    - Schema fallback: it only happens when the 400 error message is about the
      response schema. API_KEY_INVALID and other 400s (e.g. a bad image) fail
      after one call. The fallback request also gets the 503/429 retries.
    - Timeouts and network errors are logged and turned into
      VisionUnavailableException, which ErrorHandler already maps to 503.
      Interruptions are handled the same way. Timeouts are not retried.
    - Redaction: before logging, the configured key, any AIza… key and any AQ.…
      key (AQ\.[0-9A-Za-z_\-.]{20,}) are replaced with [redacted]. I used the
      same patterns as tools/check_secrets.py. Messages are capped at 500
      characters.
    - The app only sees short messages like "Gemini returned HTTP 503 after 3
      attempts". Gemini's own error text goes only to the log.
  - VisionLog.java: every line now has attempts. Failed calls add errorKind
    (http, timeout, network or interrupted) and error, and use status: 0 when no
    response arrived.
  - ErrorHandler.java: no change was needed. I didn't add a catch-all that turns
    every IOException into 503, because that would also hide unrelated errors
    such as a broken upload. The API contract is unchanged.

  AQ.-format tests (your correction): there are three:
  - a redaction test with all three key formats in one string;
  - a test where the configured key is an AQ. key and Gemini echoes it back in
    its error; neither the log nor the message to the app contains the key or
    any fragment of it;
  - a test where an AQ. key that isn't the configured key is still redacted.
